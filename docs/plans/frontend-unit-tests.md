# Frontend Unit Tests Plan

**Status:** Done — every area in the Progress table is Done, Skipped, or Out of Scope; no Partial rows remain.
**Created:** 2026-08-19
**Goal:** Build vitest unit test coverage across `frontend/src/*`, one area at a time. Same priority order as the backend plan (`docs/plans/backend-unit-tests.md`): pure-logic modules first, then rendering/behavior of shared and feature components, thin page-level wiring last (or skipped where it's just composition).

**Scope:** `frontend/src/lib/*`, `frontend/src/features/*/*` (non-component logic first, then components), `frontend/src/components/ui/*`, `frontend/src/components/patterns/*`, `frontend/src/components/*` (flat legacy). Out of scope for now: `frontend/src/pages/*` (mostly composition of already-tested feature components plus routing/context — revisit only if a page grows real logic of its own), `frontend/src/App.tsx`/`main.tsx`/`vite-env.d.ts` (routing bootstrap, no branching logic worth testing standalone).

## Setup

Already in place before this plan started: `vitest` + `happy-dom` devDependencies, `npm run test` script (`frontend/package.json`), and a `test` block in `frontend/vite.config.ts` (`environment: "happy-dom"`, `include: ["tests/**/*.test.{ts,tsx}"]`).

Added to start this plan:

- `@testing-library/react`, `@testing-library/jest-dom`, `@testing-library/user-event` devDependencies.
- `frontend/tests/setup.ts` (imports `@testing-library/jest-dom/vitest`), wired via `test.setupFiles` in `vite.config.ts`.
- Root `npm run test` now runs backend then frontend (`package.json`); `npm run check` picks this up automatically.

Fixed during `lib`/`components/ui` coverage: `frontend/tests/setup.ts` was missing an `afterEach(() => cleanup())` (`@testing-library/react`) — without it, renders from earlier tests in the same file stayed in the DOM and broke `getByRole`/`getByText` queries in later tests once a suite had more than one `render()` per file. Now registered globally in `setup.ts`, so individual test files don't need their own cleanup.

## Conventions

- Test files live in `frontend/tests/<mirror-of-src-path>.test.ts(x)`, mirroring `frontend/src/<path>.ts(x)` (e.g. `src/lib/cx.ts` → `tests/lib/cx.test.ts`, `src/components/ui/Pill.tsx` → `tests/components/ui/Pill.test.tsx`).
- Use vitest's own `describe`/`it`/`expect` (not `node:assert`) — unlike the backend plan, jest-dom's matchers (`toBeInTheDocument`, `toHaveClass`, etc.) only extend vitest's `expect`, so staying on one assertion style avoids mixing conventions within the same suite.
- Pure-function/logic modules (`lib/*`, `features/*/  *Types.ts` transforms, `*Format.ts`, `*Helpers.ts`, `*Display.ts`, non-component `.ts` files generally) need no rendering setup — plain `describe`/`it`/`expect`.
- Component tests use `@testing-library/react`'s `render`/`screen`; prefer `screen.getByRole`/`getByText` queries over container/class selectors, falling back to `container.querySelector`/`toHaveClass` only for presentational details (tone classes, indicator dots) with no accessible role/text.
- User interaction (clicks, typing, form submission) uses `@testing-library/user-event`, not `fireEvent`, for realistic event sequencing.
- `frontend/src/lib/api.ts` (the shared fetch wrapper) and any `features/*/  *Api.ts` client module: mock at the boundary the module owns — stub `global.fetch` with `vi.stubGlobal("fetch", vi.fn())` in `beforeEach`/`afterEach` (`vi.unstubAllGlobals()` after), same pattern as the backend's network-mocking convention. Modules that call into `lib/api.ts` rather than `fetch` directly should mock `lib/api.ts` itself via `vi.mock`.
- Components that depend on context providers (`AuthProvider`, `ToastProvider`) need a small test-local wrapper providing the context, not a re-implementation of the provider's internals — prefer rendering the real provider with minimal/mocked inputs over hand-rolling a fake context value, unless the provider itself does network calls that need mocking first.
- Hooks (`use*.ts`) are tested through the components that use them where practical; reach for `@testing-library/react`'s `renderHook` only when a hook has meaningful standalone branching logic not otherwise exercised.
- Page components (`pages/*`) are out of scope for the same reason backend routes are: thin wiring over already-tested pieces. Revisit a specific page only if it grows real logic beyond composition + routing.
- Components with real state that a controlled prop feeds back into (e.g. `PinField`'s `value`/`onChange`) need a small local wrapper component holding `useState` in the test, not a bare `vi.fn()` for `onChange` — a fixed prop value makes typed-character assertions reflect React re-render/reset behavior instead of the component's actual behavior when wired up normally.
- Timer-driven open/close behavior (`Tooltip`'s hover delays) needs `vi.useFakeTimers()` + `fireEvent.mouseEnter`/`mouseLeave` + `act(() => vi.advanceTimersByTime(...))`, not `userEvent.hover`/`unhover` — `user-event`'s internal waits deadlock against `vi.useFakeTimers()` even with `advanceTimers` configured. Always pair `vi.useFakeTimers()` with an `afterEach(() => vi.useRealTimers())` so a timed-out/failed test doesn't leak fake timers into later tests in the same file. Click-driven toggle behavior (no delay) still uses plain `userEvent` with real timers.
- File input change tests that need to assert a *rejection* path (wrong type/extension) can't use `userEvent.upload()` — it silently filters the file against the input's `accept` attribute itself, so a mismatched file never reaches the component's `onChange` at all. Instead build a `FileList`-like object by hand (`Object.assign([file], { item: (i) => [file][i] ?? null })`), assign it via `Object.defineProperty(input, "files", { value, configurable: true })`, and fire the change with `fireEvent.change(input)`. Accepted-file cases can still use `userEvent.upload()` normally.
- A component under test that pulls in unrelated feature modules with their own network calls or heavy internals (`AppShell.tsx` importing `features/status/statusApi`, `features/update/updateApi`, `features/feedback/FeedbackModal`) mocks those sibling modules directly with `vi.mock("../../src/features/.../module", () => ({ ... }))` rather than mocking `fetch`/`lib/api.ts` underneath them or rendering their full internals — keeps the test scoped to the component's own composition/branching logic. First used for `AppShell.test.tsx`.
- Testing a fallback action that calls `window.location.reload()` (`ErrorBoundary`'s reload button) needs `Object.defineProperty(window, "location", { value: { ...window.location, reload: vi.fn() }, writable: true, configurable: true })` before rendering — `window.location` isn't directly reassignable/spy-able otherwise in happy-dom.
- Class components with `componentDidCatch` (`ErrorBoundary`) log the caught error via `console.error` by design; spy on `console.error` with `vi.spyOn(console, "error").mockImplementation(() => {})` in the throwing test(s) and `vi.restoreAllMocks()` after, so the expected caught-error log doesn't show up as test noise.
- `userEvent.setup()` installs its own clipboard emulation the first time it runs, which silently replaces a `vi.stubGlobal("navigator", { ..., clipboard: { writeText: vi.fn() } })` mock set up beforehand (`navigator.clipboard.writeText` reverts to the real `AsyncFunction`, so `toHaveBeenCalledWith` fails with "is not a spy"). For a test that both stubs clipboard and needs to click something, use the bare `userEvent.click(...)` (no `const user = userEvent.setup()`) for that interaction, same as `CopyableCode.test.tsx`/`CopyField.test.tsx` already do — first hit in `Esp32FirmwareSetup.test.tsx`.
- `react-router-dom` v7's `useBlocker` (navigation-blocking, e.g. leave-confirmation on a dirty form) needs a data router (`createMemoryRouter`/`RouterProvider`), not plain `MemoryRouter` — since exercising real navigation blocking is react-router's own concern, not the component's, mock just that one export via `vi.mock("react-router-dom", async (importOriginal) => ({ ...(await importOriginal()), useBlocker: () => mutableBlockerRef.current }))` and drive `state`/`proceed`/`reset` directly per test, keeping the rest of the module (`Link`, etc.) real under a plain `MemoryRouter`. First used in `CreateWorkflowWorkspace.test.tsx`.
- `getByPlaceholderText`/`getByText` normalize whitespace (collapsing runs of spaces/newlines to one space) before matching, including against `RegExp` matchers — a regex asserting literal repeated spaces (e.g. `/Port {9}Protocol/` against a fixed-width table-header placeholder) will never match. Match on a distinctive single-spaced substring instead, or match multiple candidate elements with `getAllByText`/`getAllByDisplayValue` and filter by tag when a value/label can appear in more than one place (readonly command-preview textareas plus an inline summary). First hit in `Esp32FirmwareSetup.test.tsx`.
